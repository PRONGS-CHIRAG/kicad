# KiCAD Mitos — Full MVP Plan

## 1. Product overview

The MVP is a **natural-language batch-editing copilot for KiCAD**.

A user selects multiple components in KiCAD and describes the intended outcome:

> “Connect this ESP32 to the temperature sensor using I²C and add the required pull-up resistors.”

The system:

1. Reads the selected components.
2. Understands the requested outcome.
3. Creates a structured action plan.
4. Shows the plan to the user.
5. Executes the approved actions through KiCAD Mitos.
6. Runs KiCAD ERC/DRC tests.
7. Accepts the changes or restores the previous project.

The MVP is not intended to replace normal KiCAD controls. Users continue using the mouse for precise, simple operations. Natural language is used when one instruction represents several related PCB actions.

---

# 2. Core value proposition

> Describe a multi-step circuit change once, preview it, execute it in KiCAD and verify it using KiCAD’s own engineering checks.

The differentiation is not simply “control KiCAD with text.” It is:

* Multi-component changes from one instruction.
* A reviewable plan before execution.
* Deterministic validation after execution.
* Automatic rollback when a change fails.
* Evidence showing why a change was accepted or rejected.

---

# 3. Target user

The initial user is:

* An electronics student.
* A hardware hacker.
* A junior PCB designer.
* A software engineer building an electronics prototype.
* A researcher who understands the desired circuit but is slower with KiCAD.

The MVP is not intended to certify production-ready circuit boards.

---

# 4. Core MVP use case

## Selected use case

> Connect multiple selected components according to a common interface or a clearly described connection pattern.

## Primary demo

The user selects:

* An ESP32.
* An I²C temperature sensor.

The user enters:

```text
Connect these components using I²C with 3.3 V logic.
Add the required pull-up resistors.
Do not modify the USB circuit.
```

The system proposes:

* Sensor VCC → 3V3.
* Sensor GND → GND.
* Sensor SDA → ESP32 SDA pin.
* Sensor SCL → ESP32 SCL pin.
* Add SDA pull-up resistor.
* Add SCL pull-up resistor.
* Connect both pull-ups to 3V3.

After user approval, the system executes the operations and runs KiCAD ERC.

# 5. MVP scope

## Must-have features

### 1. KiCAD project loading

The system must:

* Open an existing KiCAD project.
* Read the schematic.
* Read component references.
* Read symbol names and values.
* Read pin names and pin numbers.
* Read existing nets.
* Identify selected or user-specified components.

### 2. Multi-component selection

The user can provide components through either:

* Current KiCAD selection, if Mitos exposes it.
* Component references such as `U1` and `U2`.
* A small component-selection interface in the web application.

### 3. Natural-language instruction

The user can describe:

* Which interface to use.
* Which components to connect.
* Required supporting components.
* Constraints.
* Areas that must not be changed.

### 4. Structured plan generation

The instruction is converted into a fixed JSON action plan.

### 5. Plan preview

Before changing KiCAD, show:

* Components that will be changed.
* New components that will be added.
* Proposed pin connections.
* Constraints.
* Assumptions.
* Potential warnings.

### 6. User approval

The user must approve the plan before execution.

### 7. KiCAD execution

The approved plan is executed using the available Mitos MCP tools.

### 8. KiCAD validation

Run:

* ERC after schematic or connection changes.
* DRC when the PCB layout is changed.
* Project-readability checks.
* Expected-change verification.
* Unauthorized-change detection.

### 9. Accept or rollback

* Accept changes that pass validation.
* Restore the previous project if critical validation fails.
* Request review for uncertain but technically valid results.

### 10. Validation report

Show why the operation passed or failed.

# 7. Supported circuit pattern

Start by supporting only **I²C connections**.

This is a good MVP pattern because it commonly requires several related connections:

* Power.
* Ground.
* SDA.
* SCL.
* One SDA pull-up resistor.
* One SCL pull-up resistor.

After the core workflow works, add:

1. SPI.
2. UART.
3. GPIO peripheral.
4. Simple power connection.

Do not start with all protocols simultaneously.

## Main components

### Web interface

Responsible for:

* Project selection.
* Component selection.
* Natural-language input.
* Plan preview.
* User approval.
* Validation results.
* Before-and-after summary.

### Backend API

Responsible for coordinating the complete workflow.

### KiCAD state reader

Extracts:

* Symbols.
* References.
* Pins.
* Pin types.
* Existing connections.
* Power nets.
* Existing supporting components.
* Project rules.
* Existing ERC/DRC results.

### LLM plan converter

Converts natural language and KiCAD context into structured JSON.

### Plan validator

Checks that:

* Referenced components exist.
* Referenced pins exist.
* The protocol is supported.
* The plan uses allowed action types.
* Protected objects are not modified.
* Required information is available.
* Every generated action conforms to the schema.

### Mitos MCP client

Executes approved structured actions through the four available Mitos tools.

### KiCAD validation service

Runs KiCAD checks and normalizes their results.

### Deterministic decision engine

Decides whether to:

* Accept.
* Reject and restore.
* Request user review.

The LLM must not make the final pass/fail decision.

# 13. Prevent duplicate additions

Before adding supporting components, inspect the existing schematic.

For example, before adding pull-up resistors:

1. Check whether SDA already has a pull-up.
2. Check whether SCL already has a pull-up.
3. Determine the connected voltage.
4. Inspect the existing resistor value.
5. Add a resistor only if an acceptable one is missing.

Otherwise, the system could create duplicate or conflicting components while still passing basic ERC.

---

# 14. Defining a right move

A batch of changes is considered correct only when all hard checks pass.

## Hard checks

* The KiCAD project remains readable.
* The intended components exist.
* The requested connections were created.
* Required supporting components were added or already existed.
* Protected components and nets were not modified.
* No unauthorized object was changed.
* No new critical ERC violations were introduced.
* No conflicting nets were connected.
* Explicit user constraints were followed.

## Example

The instruction is:

> “Connect U3 to U1 using I²C with 3.3 V logic.”

A correct result must contain:

```text
U3.SDA → MCU SDA pin
U3.SCL → MCU SCL pin
U3.VCC → 3V3
U3.GND → GND
SDA pull-up → 3V3
SCL pull-up → 3V3
```

It must not:

* Connect the sensor to 5 V.
* Connect SDA and SCL together.
* Create duplicate pull-ups unnecessarily.
* Modify the protected USB circuit.
* Introduce new critical ERC errors.

---

# 15. Defining a wrong move

Reject the batch if:

* A nonexistent component or pin was used.
* The wrong components were modified.
* The requested connections were not created.
* Two incompatible power nets were connected.
* A ground pin was connected to a power rail.
* An output was incorrectly connected to another output.
* Protected objects were changed.
* Unexpected components or wires were added.
* The project became unreadable.
* New critical ERC/DRC violations appeared.
* Execution stopped halfway and left a partial circuit.

All actions in one instruction should behave as a transaction:

> Either the entire approved batch succeeds, or the complete batch is reverted.

# 16. Grounding in truth with KiCAD

## Before execution

Run KiCAD ERC and store the baseline.

```json
{
  "baseline": {
    "errors": 1,
    "warnings": 3,
    "violations": []
  }
}
```

Existing errors should not automatically block the action. The important check is whether the new operation introduces additional errors.

## After execution

Run ERC again and calculate:

```text
New violations = after − before
Resolved violations = before − after
Unchanged violations = before ∩ after
```

Do not compare only error counts. The system must compare the actual violations.

For example:

* One old error disappears.
* One dangerous new error appears.
* The count remains the same.

A count-only comparison would incorrectly accept the change.

## KiCAD CLI

The backend should discover the installed version and supported commands:

```bash
kicad-cli --version
kicad-cli sch erc --help
kicad-cli pcb drc --help
```

Then run the corresponding ERC or DRC command and parse its output.

## Additional deterministic checks

KiCAD ERC alone does not prove that the requested result happened. Therefore also inspect:

* Pin-to-net assignments.
* Net membership.
* Component additions.
* Symbol values.
* Protected object hashes.
* Unexpected file differences.

# 17. Validation pipeline

```mermaid
flowchart TD
    P["Approved plan"] --> B["Save baseline"]
    B --> E["Execute complete batch"]
    E --> F["Verify expected file changes"]
    F --> K["Run KiCAD ERC/DRC"]
    K --> C["Compare project states"]
    C --> D{"All hard checks pass?"}
    D -->|Yes| A["Accept"]
    D -->|No| R["Restore entire checkpoint"]
    D -->|Cannot determine| H["User review"]
```

## Validation order

1. Did the MCP execution complete?
2. Can KiCAD process the modified project?
3. Were all expected actions performed?
4. Were any unauthorized actions performed?
5. Were protected items preserved?
6. Did KiCAD report new critical violations?
7. Do the final connections match the approved plan?

# 19. Checkpoint and rollback

Before applying changes:

* Copy `.kicad_pro`.
* Copy `.kicad_sch`.
* Copy `.kicad_pcb`, if relevant.
* Copy local symbol or footprint files if they may change.
* Calculate SHA-256 hashes.
* Store the original ERC/DRC reports.
* Store the structured project state.

If validation fails:

1. Restore every checkpointed file.
2. Compare restored hashes with original hashes.
3. Run ERC again.
4. Confirm that the original project state returned.

Do not attempt to reverse individual actions manually. Restore the entire known-good checkpoint.

* Request user clarification.

## Benchmark 4: Wrong voltage request

The user requests 5 V for a 3.3 V-only component.

Expected:

* Reject or warn before execution.
* Make no changes.

## Benchmark 5: Protected circuit

The user protects the USB circuit.

Expected:

* No USB-related objects change.

## Benchmark 6: Existing ERC warnings

The project starts with unrelated warnings.

Expected:

* Preserve baseline warnings.
* Do not incorrectly blame the new operation.

## Benchmark 7: Deliberately wrong connection

Cause the executor to connect SDA to GND.

Expected:

* Detect the difference from the approved plan.
* Reject the batch.
* Restore the checkpoint.

## Benchmark 8: Partial execution failure

Stop after completing three of six actions.

Expected:

* Reject the incomplete batch.
* Restore all files.

## Benchmark 9: Unknown component

Expected:

* Reject before execution.

## Benchmark 10: Ambiguous instruction

```text
Connect the sensor properly.
```

Expected:

* Ask which interface and logic voltage to use.

# 21. Evaluation metrics

| Metric                   | Meaning                            |        MVP target |
| ------------------------ | ---------------------------------- | ----------------: |
| Plan accuracy            | Correct structured plans           |              ≥80% |
| Execution success        | Approved plans executed completely |              ≥80% |
| Unsafe-change rejection  | Dangerous changes detected         | 100% on benchmark |
| Rollback success         | Failed changes fully restored      |              100% |
| Unauthorized-change rate | Changes outside approved scope     |                0% |
| Duplicate-component rate | Unnecessary supporting parts       |                0% |
| Project-corruption rate  | Unreadable KiCAD projects          |                0% |
| Median completion time   | Instruction to result              |  Under 60 seconds |

Safety metrics matter more than raw completion rate. It is better to reject an uncertain instruction than silently produce an incorrect connection.

# 29. Final MVP definition

The MVP is complete when a user can:

1. Open a KiCAD project.
2. Select an MCU and one peripheral.
3. Describe an I²C connection in natural language.
4. Review a structured connection plan.
5. Approve the plan.
6. Execute the complete batch through Mitos.
7. Run KiCAD ERC.
8. Verify the expected connections.
9. Detect unexpected changes.
10. Accept the result or automatically restore the project.

The final positioning should be:

> **KiCAD Mitos turns high-level circuit intent into reviewable multi-step changes, executes them inside KiCAD and verifies the result against the real project using KiCAD’s own engineering checks.**
 Implement everything, break it into subproblems and use subagents to implement everything.
