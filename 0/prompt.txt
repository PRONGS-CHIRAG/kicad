### Symbol 1 — `MCU:ESP32-DEVKITC-32` (value `ESP32-DEVKITC-32`, ref `U1`)

`lib_id` contains "esp32" so `_is_controller` fires on the lib hint, not just the pin heuristic.

| # | name | etype | why |
|---|---|---|---|
| 1 | 3V3 | power_in | listed first so `_supply_net` returns the +3V3 rail, not GND |
| 2 | GND | power_in | |
| 5 | GPIO5 | bidirectional | classic ESP32 VSPI CS |
| 18 | GPIO18 | bidirectional | VSPI SCK |
| 19 | GPIO19 | bidirectional | VSPI MISO |
| 21 | GPIO21 | bidirectional | I2C SDA default |
| 22 | GPIO22 | bidirectional | I2C SCL default |
| 23 | GPIO23 | bidirectional | VSPI MOSI |
| 25 | GPIO25 | bidirectional | spare GPIO |
| 30 | SCK | output | controller drives clock |
| 31 | MOSI | output | controller drives data out |
| 32 | MISO | input | controller listens |
| 33 | CS | output | controller drives select |
| 34 | TX | output | |
| 35 | RX | input | |
| 36 | EN | input | tied to +3V3, mirrors the existing fixture idiom |

Two deliberate choices:
- **Pin numbers mirror the GPIO number** (`GPIO18` is pin `"18"`). `Component.pin()` matches name *or* number, so with 1..16 numbering `pin("5")` would have returned `GPIO19`. Alias pins sit on 30–36, outside `{5,18,19,21,22,23,25}`, so name- and number-resolution can never disagree.
- **Both matching paths coexist on the same symbol**: alias-matching finds literal `SCK`/`MOSI`/`MISO`/`CS`/`TX`/`RX`, and the explicit-answer path (or a `default_controller_pin="GPIO18"`) finds the plain GPIOs. Verified: `_answered_pin(u1,"GPIO25")`, `("25")`, `("18:GPIO18")` all resolve; the clarification option list `[p.name for p in pins if CONTROLLER_PIN_HINT.match(p.name)]` yields exactly the 7 GPIOs.

### Symbol 2 — `Display:ILI9341` (value `ILI9341`, SPI peripheral)
`1 VCC power_in`, `2 GND power_in`, `3 SCK input`, `4 MOSI input`, `5 MISO output`, `6 CS input`. MISO is a real `output`, which is the whole point: it makes "reject only when BOTH endpoints are outputs" distinguishable from the I2C "reject any output" rule.

### Symbol 3 — `RF:HC-05` (value `HC-05`, UART peripheral)
`1 VCC power_in`, `2 GND power_in`, `3 TX output`, `4 RX input`. The crossover `U1.TX(output) -&gt; U2.RX(input)` and `U1.RX(input) -&gt; U2.TX(output)` are both electrically valid; `TX-&gt;TX` would be two outputs.

### Symbol 4 — `Relay:RELAY_2CH` (value `RELAY-2CH`, GPIO peripheral)
`1 VCC power_in`, `2 GND power_in`, `3 IN1 input`, `4 IN2 input`, `5 FAULT output`. No aliasable signal names at all, so GPIO must ask for both pins. `IN1`/`IN2` do not match `^(GPIO|IO|P[A-D])\d+$`, so it stays a peripheral. Answer forms `"3:IN1"`, `"IN1"`, `"3"` all resolve to `IN1`.

### Symbol 5 — `Device:Fan` (value `FAN_5015`, power-only)
`1 VCC power_in`, `2 GND power_in`. Nothing else.

**Both-outputs rejection pair the next agent needs:** `U1.TX` (output) ↔ `U2.FAULT` (output) in `esp32_gpio_peripheral`, or `U1.TX` ↔ `U2.MISO` (output) in `esp32_spi_display`. Valid-direction pairs: `U1.SCK/MOSI/CS (output) -&gt; U2.SCK/MOSI/CS (input)`, `U2.MISO (output) -&gt; U1.MISO (input)`.

The peripheral is entirely unwired in all four — that is the planner's work. **The MCU must stay in `esp32_power_only`:** the reader skips power-symbol pins when building `nets`, so `+3V3`/`GND` only become resolvable by `_resolve_rail` because the MCU's `3V3`/`GND` pin labels put them there. Trim U1 and every POWER plan fails with `incompatible_voltage`. Confirmed for all four: `_is_controller(U1)=True`, `_is_controller(U2)=False`, `_supply_net(U1)="+3V3"` (== rail, so no `incompatible_logic_voltage`), `VCC`/`GND` resolve on every peripheral.

**No `.kicad_pcb` on the new projects** — one dedicated board fixture (`esp32_i2c_board`) is the pattern, and `build_board` is hardcoded to the ESP32/TMP102/USB footprints.

## ⚠️ Collision the next agent must know about

`SCL_NAMES = ("SCL","SCK","I2C_SCL","CLK")` in `generator.py`, and resolution order puts `_pin_by_names` **before** the `GPIO22` default. Verified: on the new MCU, `_pin_by_names(u1, SCL_NAMES) -&gt; "SCK"` (pin 30, an `output`). So an **I2C** plan against any of the four new fixtures resolves SCL to an output pin and gets rejected by the I2C `shared_outputs_forbidden` rule, never reaching the GPIO22 default. Do not run I2C against the new fixtures. I kept the name `SCK` because the task requires the alias path to be testable; renaming to `SCLK` would break it. The five I2C fixtures use the old `MCU:ESP32-WROOM-32` symbol and are completely unaffected.
